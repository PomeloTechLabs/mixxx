### 0.1 实际使用流程

1. 解压 `dist/ohos-migration/PomeloMixxxMigration-portable.zip`，运行 `PomeloMixxxMigration.exe`，无需安装 Python。
2. 关闭 PC Mixxx，点击“读取本机 Mixxx 配置”，直接读取自动识别的配置目录；自定义位置用“选择其他配置目录”，不要求先压缩。已有 cfg/RAR/ZIP 可从备份入口读取。为各旧音乐根选择当前对应文件夹；原音乐路径仍有效时自动关联，同名不猜测，大小变化须确认，单首可手工指定。
3. 勾选“携带音乐”，按需携带波形缓存，生成并校验 ZIP。来源配置、数据库及音乐不改写。
4. 将包复制到 `Download/com.pomelo.mixxx`，在原“选项 → 导入 Windows 迁移包”选择，确认携带/缺失数量后导入，再关闭并重新打开应用。
5. 音乐落到 `Music/Imported/<档案 ID>`，私有设置和数据库落到 `files/profiles/<档案 ID>`；“配置档案／还原 → 本机原始档案”可切回，该操作不删除音乐。

新档案沿用本机可播放的 `soundconfig.xml`，不套用 Windows 声卡配置。数据库升级使用原 SchemaManager，保留歌曲/location/CUE/列表 ID。运行日志及导入摘要在 `Download/com.pomelo.mixxx/logs`；公共摘要导出失败只警告，不误报已保存档案失败。

设置和数据库按档案保存，公共 Music 全根共用；启动扫描可发现其它档案导入的音频。切换档案不移动这些文件，也不等同于撤回公共目录新增歌曲。

## 1. 范围与原则

- 主界面、皮肤布局及 Mixxx 控制语义保留；调整输入解释、命中范围、滚动和弹窗适配。新增功能入口放入原菜单/设置。
- 根据每次事件的输入设备区分 TouchScreen、Mouse、Keyboard。Phone/Pad 外接鼠标仍使用原左/右键、拖动、滚轮；物理键盘仍使用原快捷键。触摸规则仅处理触屏事件及其合成事件，混合使用无需手动切换整套模式。
- 显示缩放与输入灵敏度分开。手势阈值按设备无关距离配置，经实际窗口映射转换；全屏、分屏、浮窗、方向变化使用同一坐标链路。
- 演奏按钮保留立即按下、按住和松手语义；不能用全局长按右键覆盖 CUE/Hotcue/LongPressLatching。

## 2. 推荐触摸规则

| 控件/区域 | 推荐操作 | 处理方式 |
|---|---|---|
| 曲库行 | 轻触选中；双击沿原加载设置执行 | 滑动手势不再补发点击，播放中的 Deck 保留原防误加载保护 |
| 曲库/目录/设置长页 | 单指滑动 | 按区域支持纵向或横向滚动；惯性只作用列表，不作用音量/音调/波形 |
| 曲库歌曲拖放 | 按住至准备状态，再移动到 Deck/歌单 | 保留当前长按拖歌能力；推荐改为达到长按阈值后等待移动才启动原 QDrag，拖动后不再弹菜单 |
| 曲库右键菜单 | 长按达到阈值，保持原位松手 | 弹出原 WTrackMenu；与上一行用松手/移动区分，先开菜单再拖歌会发生冲突，不采用这种顺序 |
| 曲库多选 | 原菜单增加触摸多选入口；进入后轻触增减选择 | 复用原 selectionModel，支持批量拖放/歌单操作；退出多选可达，不要求 Ctrl |
| EQ/增益/效果旋钮 | 单指上下拖；双击复位 | 触摸只用相对位移，减少斜向抖动；数值沿用原 control 和原显示。可配置灵敏度及精细调节，无隐藏光标/光标回位 |
| 推子/Crossfader/Pitch | 沿推子方向拖；双击按原规则复位 | 触下保持当前值再相对拖动，避免碰到轨道时突然跳值；捕获当前手指，滑出可继续、松手结束 |
| CUE/Hotcue/按住类按钮 | 按下立即触发，松手立即释放 | 不为识别长按延迟演奏操作；原预听、锁定语义保留，不用长按直接删除 CUE |
| Hotcue 编辑/交换 | 从原菜单进入触摸编辑；点槽位开原 CueMenu，拖槽位交换 | 编辑状态下不触发演奏；完成/取消返回。解决编辑与按住预听竞争，保留原 CueMenu 和 swapHotcues 行为 |
| 波形/转盘 | 按区域保留原定位、推碟/搓碟操作 | 不对波形启用列表惯性或通用长按菜单；触摸始终归属开始命中的控件 |
| 其它右键/修饰键功能 | 原菜单提供一次性“下一次触摸使用右键/修饰操作”入口 | 只在下一次明确点击时调用目标原有次级操作，然后自动退出；作为未单独适配控件的补充，不作为常用主操作 |

长按建议初值 600–700 ms、移动阈值约 8–12 vp，需在实体手机和平板调整；不是已验证的最终参数。曲库长按准备时用原选择高亮及可选轻震反馈。用户可配置长按时间、灵敏度、双击行为，并保存设置。

### 2.1 曲库手势如何避免冲突

1. 按下进入候选状态。短时间松手是点击；达到移动阈值且未长按，是滚动。
2. 静止达到长按阈值进入准备状态；此时只给反馈，不打开菜单、不启动 QDrag。
3. 准备后移动超过阈值才启动原拖放；准备后原位松手打开原右键菜单。
4. 已滚动不转成拖歌；已拖歌不触发点击/菜单。系统取消、失焦、旋转/窗口几何变化时清理状态，拖放结果按原业务规则处理。

P1.17 已改为长按准备后移动才启动 QDrag；原位松手开原歌曲菜单，平板通过。

### 2.2 小屏与多指

- Phone 默认使用较低调节灵敏度，减少手指遮挡；Pad 使用较大距离进行调节。两者可独立保存触摸设置。
- 扩大触摸命中范围只使用相邻控件之外的空隙；重叠区域按最近目标/实际控件内点确定。密集主界面不能保证所有控件达到大尺寸目标，极小窗口继续提示放大。
- 保留原菜单、下拉与对话框，只让超出屏幕的内容可滑动、操作按钮可达；不将包含原生 GL 波形的主面板整体包进 QScrollArea。
- 支持一指推子、一指 EQ 等独立操作时，需要按 pointer ID 分派到各控件，不能把所有手指压成单一鼠标。多指不作为右键默认手势，避免抢占混音操作。按下/释放/取消均成对处理，退后台或失焦不留下卡住的 CUE。
- 第一阶段先稳定单指；多指并行作为独立验收项。不能把 Qt 接收 TouchEvent 等同于混音多控件已可同时调节。

## 3. Windows 配置迁移入口

原“选项/设置”中增加“导入迁移包”。首版以简单 PC 工具“旧柚Mixxx迁移助手”为主要入口：用户选择旧备份和音乐位置，工具生成跨平台配置副本、收集数据库及实际音乐、建立显式对应清单，输出 Phone/Pad 可导入的迁移包。普通用户无需手动编辑 cfg/数据库/路径映射文件。旧配置目录 ZIP、仅 cfg 导入和设备上重新关联作为高级/兼容入口。Windows 鼠标键盘操作保持原规则。

旧 RAR 属于兼容资料来源：打包助手可读取本次 `Mixxx.rar` 并转为标准 ZIP 迁移包；OHOS 直接读取 RAR 的解码库、格式版本及资源限制需另行验证，未完成前不能声称手机可直接导入 RAR。

Windows 默认配置通常在 `%LOCALAPPDATA%/Mixxx`；应支持用户通过 `--settings-path` 指定的自定义目录。普通用户打包前关闭 Windows Mixxx；导出工具若处理运行中的数据库，应使用 SQLite backup 获取一致快照，不能只复制正在写入的 sqlite 并丢弃 WAL。

| 录音、封面、采样器、自动载入歌曲、外部资源路径 | 按类型重定位；不是对整个 cfg 做全局字符串替换 |
| 凭据/系统授权/程序或插件路径 | 系统授权在目标设备获取；Windows 可执行文件/.dll 不迁移为 OHOS 可用功能。凭据另行处理，不写入公开导入报告 |

推荐迁移包包含实际音乐，导入时写入已授权的 `Download/com.pomelo.mixxx/Music/Imported/<导入批次>`，各源根目录独立命名，保留相对子目录。只有配置的旧备份可由用户提供本机音乐目录进行重新关联；也可显式选择其它目标目录，但确认前必须验证样本音频确实可打开，不能仅检查目录可枚举。

### 3.2 路径映射与找回歌曲

导入预览自动列出所有 Windows 音乐根目录，让用户逐项指定目标：

| Windows 根目录 | 目标目录示例 |
|---|---|
| `D:/MP3TEMP` | `Download/com.pomelo.mixxx/Music/Imported/<批次>/MP3TEMP` |
| `D:/MP3/FAST` | `Download/com.pomelo.mixxx/Music/Imported/<批次>/FAST` |

例如 `D:/MP3/FAST/DISCO/a.mp3` 对应 `Music/Imported/<批次>/FAST/DISCO/a.mp3`。界面显示用户可理解的路径；内部使用系统授权后可读的 URI/物理路径。登记根以外的歌曲、录音和引用资源另列 extras，不能漏掉。

- 支持多个源根目录、不同目标根目录、映射保存和下次复用；优先匹配最长目录前缀，并按目录分隔符边界比较，避免 Music 误命中 Music2。
- 按 Windows 规则解析盘符、反斜杠和 UNC；目标路径保留实际大小写。处理 Unicode、空格、重名及目标路径冲突，不直接把 Windows 字符串送给 OHOS QFileInfo canonicalize。
- 顺序：用户确认的根映射/相对路径 → 同文件内容可验证的候选 → 交互处理疑义。仅凭同名、标题、时长不能自动把另一首歌的 CUE 绑定过去；原库没有文件摘要时应明示匹配依据和置信程度，必要时保留待处理。
- 歌曲路径、目录、独立封面、采样器、录音位置和其它资源分别处理。音乐未复制/无权限/重名冲突分别报告，未匹配条目保留为缺失，可稍后重新关联，不删除歌单/CUE。
- 预览显示“可迁移/文件未到位/无权限/冲突/不支持”数量，提供样本列表，用户确认后应用。

#### 3.2.1 配置与音乐一起打包：显式清单关联

迁移包建议结构如下，包内路径全部相对化：

```text
manifest.json
portable-settings.json
config/Mixxx/mixxx.cfg
config/Mixxx/mixxxdb.sqlite
config/Mixxx/effects.xml、effects/、samplers.xml、可选映射
audio/root-001/<原相对子目录与文件>
audio/root-002/<原相对子目录与文件>
audio/extras/<资源标识与文件>
artwork/<独立封面>
analysis/<可选缓存>
```

- manifest 包含格式版本、packageId、来源 Mixxx/schema 版本、根目录规则、打包范围、分卷清单，以及每条源 track ID/location ID 对应的资源 ID、包内相对路径、实际字节数、SHA-256、可选音频属性和缺失原因。
- portable-settings.json 保存已分类的便携设置和路径策略；旧 cfg 为兼容参考。PC 工具不硬编码目标设备的沙箱绝对路径，Phone/Pad 根据实际授权目录重建最终 cfg；来源配置中的凭据不写入公开清单。
- 导出助手先从库内全部 location 和其它资源引用寻找文件，而非只看 cfg 或 directories。原盘符失效时，用户可在导出端指定当前音乐根目录，先重定位、核验再打包。
- 默认提供“全部音乐”“所选歌单/歌曲”“只带配置”三种音频携带范围，分析缓存独立可选；数据库保留完整元数据，范围外歌曲明确标记未携带。若用户选择仅导入所选曲库范围，需要按引用链筛选，保留相关 CUE/歌单顺序，不当作删除来源数据。
- 带 manifest 的导入按源 ID→包内资源→目标实际路径确定关联，验证文件摘要后重写位置并保留原 ID 关系，不依赖旧 Windows 盘符在目标设备存在。
- 多源目录内的同名歌曲分别保存；传输资源可以按内容摘要去重，但不能自动合并来源 track ID/CUE/歌单。需要保留逻辑路径时，落地为独立目标文件以满足库的唯一位置约束。
- 找不到/不可读的来源文件写入缺失清单，支持先迁移配置与元数据、以后补齐音乐。完整包验收必须显示实际携带、缺失和未选择的数量，不能只显示数据库歌曲总数。
- 分析缓存的 data_checksum 不参与歌曲匹配；只有打包助手读取真实音频得到的摘要，才可作为包内音频内容校验依据。

#### 3.2.2 旧备份没有音乐，或原路径已经丢失

本次 RAR 使用这一兼容路线：读数据库原 ID/路径 → 用户提供当前音乐目录 → 尝试根映射/相对路径 → 列出候选 → 预览并确认关联。找到后可由 Windows 助手输出完整迁移包，也可在 Phone/Pad 直接关联已复制的音乐。

旧库缺少音频 SHA-256，文件名、记录大小、时长和采样率只能筛选候选。唯一相对路径命中应显示匹配依据；同名、改名、改标签或转码等情况不能宣称已验证音频相同。发生歧义由用户选择，尚未关联条目保持缺失。

既无原路径又无文件摘要时，仍保留 track ID、原标签、CUE、歌单顺序供辅助判断；实际音频身份无法从现有元数据确定时，不自动迁移 CUE 到一个猜测文件。重新编码的音频即使是同曲，也需核对时长/偏移及关键 CUE 的落点。

#### 3.2.3 大体积、分卷与中断恢复

- 该样本记录的音乐约 12.8 GB，标准输出采用 ZIP64；对 MP3 等已压缩音频默认存储或轻压缩，配置/文本可压缩。按文件流式读写及校验，不将整包/整首大文件装入内存。
- 单包与独立多卷包均有格式定义。多卷采用一个清单及若干可独立读取的 ZIP，各卷带 packageId/序号/摘要，支持缺卷检查；不把桌面工具的 zip.001 等任意切片当成已支持格式。
- 导入前核算最终音频、缓存、临时配置和原备份占用；用户下载包本身还会占空间。选择在 Music 同一存储域内暂存再移动，避免无必要的完整音频副本。
- 校验到文件边界保存进度，恢复时核验已完成文件，支持后续补卷/补歌，不重复整个导入。通过校验的暂存内容不应被当前曲库提前扫描；需暂停扫描或排除暂存目录。
- 私有配置与公共 Music 可能属于不同存储域，不能承诺全局原子 rename。以提交日志、资源清单、活动档案标识和恢复状态协调；正式激活前所有必要资源与数据库关系完成检查。

### 3.3 覆盖、独立导入和合并

1. **仅合并选中的设置类别**：保留本机音频与平台适配，选中类别采用导入值；冲突可选保留本机。
2. **完整导入为新配置档案（推荐完整迁移默认）**：暂存源数据库和配置，保留源 track ID、歌单/CUE 关联；通过检查后切换新档案，原手机/Pad 档案保留，便于还原。需要新增配置档案选择以及启动器活动档案路径支持。
3. **合并到现有曲库（后续独立阶段）**：不能直接覆盖 DB 或仅拼接表。建立源 Track/Location/Playlist/Crate/Cue 等 ID 到目标 ID 的映射，重建全部引用；同曲不同 CUE、节拍、评级和同名歌单由冲突规则处理，默认保留本机并显示导入结果。重名歌曲不可按文件名去重。

第一版完整迁移必须含 Windows 配套打包、实际音乐携带/摘要清单、配置分类、曲库与 CUE/歌单保留、多根映射、缺失保留、流式导入、预览和还原。现有曲库合并比创建新档案复杂，作为明确的下一阶段，不能用覆盖导入冒充合并。

### 3.4 导入过程与恢复

- Windows：读取旧配置/备份 → 解析所有歌曲与资源 → 必要时映射来源音乐现位置 → 选择携带范围/缓存 → 核验实际文件并生成清单 → 输出 ZIP64 单包或独立多卷包。
- Phone/Pad：选择迁移包或旧备份 → 识别版本与携带内容 → 选择类别/档案 → 授权目标 Music/必要时关联已有音乐 → 预览文件缺失/空间/冲突 → 确认 → 流式暂存与校验 → 提交并重启 → 结果与还原。
- 所有改写先在暂存副本执行。源数据库完整性、支持的 schema、引用关系和文件可读性检查完成后，才切换活动档案/提交设置。
- 使用当前 SchemaManager 支持的升级链处理旧数据库副本；更新版本的 schema 若不支持则报告，不猜测降级。压缩包路径、解压体积/存储空间与预期文件类型应有限制，以避免不完整导入或越出暂存目录。
- 应用需要重启的配置前保存并停止当前会话、扫描/分析，关闭相关数据库连接；不得在实时音频回调里读 ZIP/写配置/迁移 DB。
- 创建备份和导入状态记录；分阶段提交与失败/崩溃恢复检查覆盖配置、数据库和资源，而非只依赖一笔 SQL transaction。回滚时恢复原活动档案，只清理本次新建且未被引用的资源，保留用户已有音乐。成功后来源副本可回滚，未解析设置留在副本。
- 结果摘要与路径映射记录写入 `Download/com.pomelo.mixxx/logs`，可另导出迁移报告；报告不含凭据。

### 3.5 简单 PC 工具：首版主要用户流程

交付形式：Windows 便携工具，解压后双击启动，无需用户安装 Python、数据库工具或手工输入命令。独立于原 Mixxx，使用简单中文向导；默认选项应适合完整迁移，高级选项折叠。

| 步骤 | 用户操作 | 工具负责 |
|---|---|---|
| 1. 选择原资料 | 自动识别本机 Mixxx 配置，或选择本次这样的 RAR/ZIP/配置目录 | 找到 cfg/数据库，识别版本及可迁移内容，读取一致的源副本 |
| 2. 找到音乐 | 原路径存在时自动找到；路径失效时选择现在存放音乐的文件夹，允许添加多个 | 自动尝试根目录/相对结构关联，展示匹配、缺失和同名冲突，仅要求用户处理疑义 |
| 3. 检查迁移内容 | 查看可携带歌曲数、缺失项、预计包体积和保存位置；默认带实际音乐 | 重建便携配置、保留 CUE/歌单/节拍关联、检查空间与资源依赖；缓存默认为可选 |
| 4. 生成迁移包 | 点击“生成迁移包” | 流式复制与核验，生成标准清单/ZIP64，显示进度、支持取消，完成后提供“打开文件夹”和缺失报告 |

在 Phone/Pad 上的默认流程简化为：选择工具生成的包 → 查看概要及空间 → 导入为新配置 → 重启加载。源根目录与包内音频已经在 PC 上对应，无需用户再次逐项配置 Windows 盘符。只有旧备份或未携带音乐时，才进入设备上的重新关联流程。

#### 3.5.1 “重制配置”的具体含义

- 读取用户原有设置，在工作副本中整理主题、布局、操作习惯、效果预设和其它可携带项；PC 的声卡、窗口位置/DPI、平台目录等转换为目标端策略。
- 原路径可从数据库解析；音乐已移动时，工具允许为一整个旧音乐根指定当前目录，一次处理该根下全部歌曲。复杂候选匹配放入后台，用户只处理明确冲突，不要求逐首拖文件。
- 保留来源 track ID 及全部需要迁移的 CUE、手工节拍、歌单顺序和历史；不通过新建空库再扫描音乐来替代迁移。
- PC 端将文件对应关系变成包内相对路径/资源 ID，目标端授权解包后再写成真实路径。数据库 schema 的目标升级调用 Mixxx 原升级链，在目标副本上完成；工具不伪造版本号或猜测目标数据库结构。
- 原配置/数据库/音频只读；重制及打包作用于副本。完整包与部分包明确区分，存在缺失时显示“带缺失记录的迁移包”，用户可选择先迁移已有内容，后来补歌。

#### 3.5.2 首版工具边界和实现方式

- 首版必须实现完整单包、同名冲突处理、源目录替换、配置整理、携带音频、ZIP64、进度/取消、空间检查和打包结束后核验。所选歌单范围、补充包、多卷作为随后增强。
- 实现可采用 Python 标准库 Tkinter、sqlite3 和支持 ZIP64 的 zipfile，打包为 Windows 便携程序；UI 与迁移核心分离，便于工具和 OHOS 共享格式说明/样本验收。
- RAR 输入在 Windows 工具侧提供经过验证的读取能力或兼容组件，验证组件分发、中文路径与 archive 版本；不能要求普通用户自行安装解压器后改命令。常用 ZIP 输出保持独立于 RAR 解码组件。
- 迁移包格式先定义版本、文件清单和各类设置策略，PC 工具与 OHOS 导入器一起验收。同一个生成包应能在 Phone/Pad 导入；PC 端生成成功不等于已通过目标端验证。
- 针对本次样本，工具应自动读出两个根及额外路径，处理 54 组同名候选，并显示 1521 条记录中实际找到/携带的数量。没有提供音乐时可检查配置并输出缺失报告，不能宣称生成了完整可播放包。

## 4. 源码依据与实现位置

- `src/platform/ohos/windowadapter.cpp`：现有原皮肤缩放、触摸 QScroller、弹窗/键盘适配。可接入区域规则与输入源区分，不继续扩大全局拦截范围。

- `src/widget/knobeventhandler.h`、`slidereventhandler.h`：已有右键/双击复位及 down/up 逻辑；触摸位移按输入源单独计算。
- `src/widget/wpushbutton.cpp`、`whotcuebutton.cpp`：LongPressLatching、PowerWindow、Hotcue 预听、右键 CueMenu、Shift 删除及拖拽交换；不能统一改写成手机长按右键。
- `src/library/dao/directorydao.cpp` 的 `relocateDirectory` 明确兼容来自其它 OS 的源目录字符串，更新目录及 track_locations，同时保留 library track ID。可作为简单整根映射的参考。
- `src/library/trackcollection.cpp` 当前 relocateDirectory 调用后直接 commit；导入不能把它直接视为失败时完全回滚的原子接口，也需要补齐封面/其它路径及冲突处理。优先在暂存档案迁移，再一次性切换。
- `src/database/schemamanager.*`、`res/schema.xml`：数据库版本与升级；效果预设位于 `effects.xml` 和 `effects/{chains,defaults}`。
- `src/preferences/configobject.*`：Mixxx 原配置语法；`src/library/dao/analysisdao.cpp`：track_analysis.id 对应缓存文件名，缓存 checksum 不能充当歌曲内容摘要。
- 新增 Windows 打包助手、清单格式及 OHOS archive/media importer；ZIP64/独立分卷/流式解包能力要明确接入并验证，当前项目未因本设计自动获得通用 RAR 解码能力。
- `src/util/cmdlineargs.cpp` 和 `QAbilityStage.ets`：当前配置目录与 OHOS 启动参数/目录授权；新增档案时需保持 Music/logs 与配置档案相互独立。

## 5. 分阶段与验收

1. **触摸基础与常用操作**：曲库滚动/长按菜单/拖放、多选、EQ/推子灵敏度和复位、Hotcue 编辑、无卡住的按住状态。Phone/Pad 分别实测；外接鼠标键盘、全屏/分屏/浮窗/正反横屏纳入验收。
2. **完整 Windows 迁移首版**：实现简单 PC 向导，自动找音乐/更换根目录/处理冲突、重制便携配置；生成配置+实际音乐的 ZIP64 单包。配套实现 OHOS 的选择包/预览/导入新配置流程；双方共享格式与清单验收。数据库/CUE/歌单保留、缺失报告、流式校验、空间检查、备份/恢复均为首版要求。该样本 schema 39→40、分析缓存关联和来源状态纳入验收。
3. **大包及补齐体验**：独立多卷包、文件级恢复/补歌、按歌单/歌曲选择携带；旧 RAR 在 OHOS 的直接读取作为独立兼容门槛。单包首版必须已经正确支持超过 4 GB。
4. **进一步优化**：多指并行、现有曲库合并、无法按相对路径关联时的辅助候选匹配。
